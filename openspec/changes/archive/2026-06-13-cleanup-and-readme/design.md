## Context

项目从最初的单文件原型演进到当前的模块化 LangGraph 架构，期间经历了多个版本的迭代（预处理→IR 召回→Schema Selection→SQL 生成→执行→决策→记忆）。每次迭代都新增了模块，但未系统性地清理旧代码。测试用例也存在"只增不减"的趋势。

此外，项目至今没有根目录 README.md，外部贡献者和团队新成员需要阅读大量代码才能理解项目结构。

## Goals / Non-Goals

**Goals:**
- 删除所有未被引用的 Python import 语句和死变量
- 删除被当前 LangGraph 子图完全取代的旧编排逻辑（如有）
- 删除覆盖已删除代码或与被测试代码严重不一致的测试用例
- 合并重复的测试 fixture 和 helper 函数
- 在项目根目录创建完整的 README.md，覆盖安装、架构、模块、API、监控、调试、开发指南

**Non-Goals:**
- 不修改任何运行时行为（纯删除和文档）
- 不重构 API 请求/响应格式
- 不增减 `requirements.txt` 依赖项
- 不修改数据库 schema 或向量存储结构
- 不优化性能（代码清理附带删除 dead code 带来的编译/启动速度提升不算优化）

## Decisions

### 决策 1：代码清理工具链 — 使用 static analysis + 人工确认
- **方案**：使用 `vulture`（死代码检测）+ `autoflake`（未使用 import 检测）作为第一轮扫描，人工 review 后批量删除
- **备选**：纯手工逐文件审查 → 太慢且易遗漏
- **理由**：vulture + autoflake 能覆盖 80% 的冗余代码，人工 review 确保不误删运行时需要的代码

### 决策 2：测试清理策略 — 只删不改
- **方案**：先运行全量测试（`pytest`）确认基线全部通过，再逐文件审查测试目录，删除以下类别：
  - 测试函数调用了已被删除的函数/类
  - 测试 mock 的接口与实际代码不匹配（run 时报错）
  - 完全重复的测试场景（同一函数有 3 个结构相同的 parametrize 用例）
- **不动**：功能正常但设计不佳的测试（那是重构阶段的事）

### 决策 3：README 结构 — 流水线式组织
- **方案**：README 按"外部用户 → 开发者 → 维护者"三层组织，从安装到高级调试逐级深入
- **备选**：按模块平铺 → 容易变成 API 文档的重复
- **理由**：这个项目是一个 pipeline 系统，按使用流程组织最自然

### 决策 4：分阶段执行
- **方案**：先清理代码，再写 README（清理后项目结构更清晰，README 更准确）
- **备选**：同时进行 → 可能 README 写完后又被清理改动，需要二次校对

## Risks / Trade-offs

- **[风险] 误删运行时路径**：Python 的动态特性（`__import__`、`eval`、`getattr` 动态调用）可能被 static analysis 遗漏 → **缓解**：每一次删除后运行全量 `pytest` 回归
- **[风险] 误删测试用例**：测试用例可能模拟了"未来修复"的场景，即使当前代码不匹配也要保留 → **缓解**：只删除那些明显指向已不存在代码的用例，不确定的标记为 `@pytest.mark.skip` 保留
- **[风险] README 快速过时**：文档写完后就与代码脱节 → **缓解**：README 首页添加 `<!-- last-updated -->` 注释标记更新日期，并在设计层面不做过于细粒度的 API 清单（指向 `pydoc` 或 OpenAPI 文档）
- **[取舍] 清理边界**：代码清理永远无法"完全干净" — 过于激进可能伤及未来扩展，过于保守则意义不大 → 本次清理以"一个 CR 能审完"为上限，不超过 30 个文件修改
